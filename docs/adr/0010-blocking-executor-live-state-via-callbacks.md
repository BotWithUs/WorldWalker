# Executor is a single blocking call that pulls live state and re-plans through callbacks

`ww_executor_run` is **one blocking call** that owns the consumer's thread for the entire walk, returning only on arrival, failure, or cancellation. The Executor reaches the game **exclusively** through a consumer-supplied callback vtable: it *reads* live state (player position, a full Capability snapshot, individual varbits, whether an interface is open), performs *actions* (walk to a Tile, interact with a loc, wait N Ticks), polls a `should_cancel` predicate each loop, and reports progress through a **nullable** `on_event` callback (step advanced, walking→interacting, teleport initiated, stuck, re-plan started, arrived/failed). Because WorldWalker is a normal CRT-linked DLL (not freestanding like NXTLibrary), the Executor reads its **own wall-clock** for stuck/action/teleport deadlines — there is no clock callback.

The Capability snapshot is **pulled live at each re-plan**, not frozen at `run()` start, so a re-plan reflects state that changed mid-walk (runes just banked, a level gained, crossing into no-teleport ground). The Planner stays pure — it only ever sees a snapshot passed as an argument — but the Executor sources that snapshot live (ADR 0004). On a re-plan trigger (reaching a teleport-allowed Tile, drift, or stuck — ADR 0009) the Executor re-invokes the Planner **in-process and synchronously**; it never yields a "needs re-plan" status to the consumer. It therefore holds the artifact handle and **borrows a search context from the bounded pool** (ADR 0007) for the duration of each in-loop re-plan, rather than merely receiving a finished Path.

The driver is the same one behind ADR 0008: the simplest possible consumer contract is "wire ~5 callbacks and call one function," never re-implement the interpreter. The prior `PathWalker` was stepped (`process()` called per tick) **only because it ran on the game thread**, where blocking would freeze the client — a constraint that does not apply here, since the Executor runs on the consumer's own thread. The accepted cost: a blocking `run()` **pins a Java virtual-thread carrier** for the walk's duration, in tension with ADR 0007's vthread parallelism; this is mitigated by running the Executor on a platform thread or raising scheduler parallelism, not by changing the model. We rejected the **stepped, consumer-pumped** model (it forces every internal wait — interface, teleport, action-interval — to be externalized as a "call me back later" status, bloating the contract) and the **blocking-on-a-WW-owned-thread** model (WorldWalker would own OS threads it otherwise never needs, and every consumer callback would have to be thread-safe against that WW thread instead of running on the caller's single thread).
