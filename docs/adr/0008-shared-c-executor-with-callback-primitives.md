# Shared C executor driven by consumer-supplied primitive callbacks

WorldWalker has two sides. The **Planner** is a pure function (artifact + start + goal + capability snapshot → Path). The **Executor** drives a Path to completion: sequencing Steps, running Transition execution chains, timing waits, detecting arrival, and re-invoking the Planner on failure. The Executor is written **once, in C**, as part of WorldWalker. It touches the game only through a small set of consumer-supplied **primitive callbacks** (walk-to-tile, interact-with-object, read-player-position, read-varbit, sleep-ticks).

The driver: if WorldWalker returned only path data, every consumer language would re-implement the executor — the genuinely hard, bug-prone part (timing, arrival detection, re-planning). Embedding WorldWalker in the C++ agent was rejected earlier (keeps it a multi-consumer C-ABI library), so the agent can't be the shared executor either. With this design a new language wires ~5 thin callbacks and never the interpreter. The cost: WorldWalker's scope grows from pure planner to planner + orchestrator, and the Executor observes/affects the game indirectly through callbacks — but the Planner stays pure, so a single immutable artifact is still shared across all clients/scripts.
