# WorldWalker

[![CI](https://github.com/BotWithUs/WorldWalker/actions/workflows/ci.yml/badge.svg)](https://github.com/BotWithUs/WorldWalker/actions/workflows/ci.yml)
[![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](LICENSE)

A speed-focused C++23 pathfinding library for RuneScape 3 (NXT engine).

WorldWalker answers one question — *how do I get from A to B* — and returns an
ordered list of steps: walk here, climb that ladder, cast this teleport, open
that door. It owns no game state. Consumers hand it a start, a goal, and a
snapshot of what the player can do; it hands back a path.

Typical query latency is **8–400 µs**, with p99 under 40 ms on cross-world
routes — against a game tick of 600 ms.

---

## How it works

Walkability splits in two, along what the game cache can and cannot tell you
([ADR 0003](docs/adr/0003-collision-from-cache-transitions-from-datasets.md)):

- **Collision** is derived fresh from the RS3 cache on every bake — per-tile
  clip flags with wall edges and corner blockers, faithful to the engine. It
  tracks weekly game updates for free.
- **Transitions** — ladders, doors, boats, fairy rings, lodestones, spell and
  item teleports — are *not* in the cache; their destinations live in
  server-side scripts. They come from curated JSON in [`datasets/`](datasets/).

Both are compiled ahead of time into a single memory-mapped artifact
(`worldwalker.wwa`, ~10 MB) holding the collision grid, a connected-component
area graph, and ALT landmark tables. At query time the planner searches the
area graph, refines to tiles within each area, and seeds the frontier with
whichever global teleports the player can actually use
([ADR 0001](docs/adr/0001-precomputed-baked-collision-artifact.md),
[ADR 0002](docs/adr/0002-hpa-star-hierarchical-pathfinding.md)).

**The runtime never touches the cache.** It opens an artifact and answers
queries. That split is what makes the library small, fast, and portable.

New to the domain vocabulary — Tile, Mapsquare, Loc, Transition, Capability
snapshot? [`CONTEXT.md`](CONTEXT.md) defines every term this codebase uses, and
names the words it deliberately avoids.

## The three targets

| Target | What it is | Needs the cache? |
|---|---|---|
| **`worldwalker`** (shared lib) | Planner + Executor + the C ABI. What consumers load. | No |
| **`wwcli`** (executable) | Dev harness: queries, benchmarks, correctness suites, the acceptance gate. | No |
| **`wwbuild`** (executable) | Offline artifact builder. Decodes the cache, ingests datasets, bakes the `.wwa`. | Yes |

Only `wwbuild` links [NXTCacheLibrary](#a-note-on-nxtcachelibrary). The runtime
library and the harness link nothing but zlib and nlohmann/json.

## Quick start

Requires Windows, MSVC (a `vcvars64` shell), CMake, and vcpkg.

```powershell
cmake -B build
cmake --build build --config Release
```

That builds `worldwalker.dll` and `wwcli.exe`. The offline baker `wwbuild` needs
a private sibling library and is skipped automatically when it is absent — see
[below](#a-note-on-nxtcachelibrary). There is nothing to configure.

`cmake.toml` is the single source of truth — `CMakeLists.txt` is generated by
[cmkr](https://github.com/build-cpp/cmkr). Never hand-edit it; adding a source
file means re-running the configure step so the globs refresh.

Then grab a prebuilt artifact from the
[releases](https://github.com/BotWithUs/WorldWalker/releases) and ask it for a
path:

```powershell
.\build\Release\wwcli.exe path worldwalker.wwa 3222 3218 0 3013 3355 0 --out path.json
.\build\Release\wwcli.exe bench worldwalker.wwa
.\build\Release\wwcli.exe check worldwalker.wwa datasets
```

`wwcli` with no arguments lists every subcommand.

## Using the library

The entire consumer surface is the C ABI in
[`src/c_api/worldwalker_c.h`](src/c_api/worldwalker_c.h) — stable, documented,
and callable from any language with an FFI (Java via Panama, C#, Python, Rust).

Planning is pure: open an artifact, create a context pool, query.

```c
ww_artifact     *art  = ww_artifact_open("worldwalker.wwa");
ww_artifact_load_teleports(art, "datasets");   /* editable without a rebake */
ww_context_pool *pool = ww_context_pool_create(art, 4);   /* one ctx per worker */

WwTile start = { 3222, 3218, 0 };        /* Lumbridge */
WwGoal goal  = { 3013, 3355, 0, 0 };     /* Falador, radius 0 = exact tile */

WwPath path;
if (ww_query(art, pool, start, goal, &capabilities, &path) == WW_OK) {
    /* path.steps is an ordered list of WALK and TRANSITION steps */
    ww_path_free(&path);
}

ww_context_pool_destroy(pool);
ww_artifact_close(art);
```

Walking is optional. If you want WorldWalker to *drive* the walk rather than
just plan it, wire about five callbacks — read position, read capabilities,
walk to a tile, interact with a loc, wait N ticks — and call `ww_executor_run`.
It blocks on your thread until arrival, failure, or cancellation, re-planning
on its own when it drifts or gets stuck. You never re-implement the interpreter
([ADR 0008](docs/adr/0008-shared-c-executor-with-callback-primitives.md),
[ADR 0010](docs/adr/0010-blocking-executor-live-state-via-callbacks.md)).

## Contributing

**Editing a teleport needs no cache, no private dependency, and no bake.**
`spell_teleports.json` and `item_teleports.json` are loaded at artifact-open
time, so a released `.wwa` plus `wwcli` is a complete working setup.

See [CONTRIBUTING.md](CONTRIBUTING.md) for the workflow, and
[`datasets/README.md`](datasets/README.md) for what each file means.

## A note on NXTCacheLibrary

Baking an artifact requires `NXTCache.dll`, which decodes the RS3 cache. That
library is currently a separate, unpublished repository — the one piece of this
project that is not yet open.

**The build handles its absence on purpose.** `cmake -B build` detects whether
the sibling is there; if it is not, `wwbuild` is dropped from the build and
`worldwalker` + `wwcli` compile normally. You get a working library and harness
from the two commands above, with no flags and no errors. Force the issue with
`-DWORLDWALKER_BUILD_WWBUILD=ON` and you get a configure-time message naming the
exact paths it looked in, rather than a link failure minutes later.

What that does and does not block:

| You want to change | Bake required? | Possible today? |
|---|---|---|
| `spell_teleports.json`, `item_teleports.json` | No — loaded at runtime | **Yes** |
| The planner, the executor, the C ABI, `wwcli` | No | **Yes** |
| `transport_links.json`, `teleport_chains.json` | Yes — baked into the graph | Open a PR; a maintainer bakes |
| The collision builder itself | Yes | Open a PR; a maintainer bakes |

The top two rows are the whole library minus the cache decoder. For the bottom
two, open a PR with your diff and a maintainer bakes and publishes the artifact.
Options for closing the gap properly are laid out in
[`docs/artifact-delivery.md`](docs/artifact-delivery.md) §7.
